智慧工廠邊緣 AI：從預測性維護到自主決策 Agent 的系統架構設計

從感測器串流、異常偵測、剩餘壽命預測，到邊緣部署與工業知識檢索，說明一套智慧工廠邊緣 AI 系統的分層架構與設計取捨。
October 18, 2026 · 12 分鐘 · Jay Fu | 語言:
  • En

TL;DR

  • 六層架構：感測 → 串流 → 訊號處理 → PHM → Edge Agent → MES／EAP 整合與安全控制。
  • 兩階段偵測（Isolation Forest → Autoencoder）加上 RUL 預測，把原始訊號轉成維護規劃；數字屬專案情境。
  • 模型依序經過影子部署、金絲雀分批發佈（5% → 20% → 100%），再做監控與回退。
  • Edge Agent、工業 RAG 與 MLOps 把證據接到工作流程，但安全關鍵控制仍留在 LLM 之外。

在擴大自主決策之前，先讓每一層都可觀測、可驗證、可回退。

前言#

本文將 11 張面試簡報延伸為智慧工廠邊緣 AI 架構的技術參考，涵蓋即時處理、異常偵測、剩餘壽命（RUL）預測、邊緣部署、工業知識檢索與 AI Agent 的決策邊界。真正的難題不是把模型部署到工廠，而是讓它在延遲、運算、可靠性與成本限制下運作，並與既有控制、維護流程及工廠系統整合。

智慧財產權與使用聲明： 本文用於技術交流、架構討論與個人能力展示，內容已去識別化，不含未公開的客戶資料、營業秘密或內部專案資訊。圖文使用與轉載請依作者公布之授權條件辦理。

01. 系統目標與設計前提#

半導體產線設備種類多、感測頻率高、停機成本高，部分控制流程對延遲與可靠性要求嚴格。架構因此採邊緣運算與集中管理並行：低延遲工作留在廠內，集中式服務負責模型管理、跨設備分析與部署；防火牆與稽核管制也讓異地即時分析不切實際。

  • 資料治理與資安： 依分級與權限處理感測資料、設備資訊與維修紀錄；敏感資料在廠內運算，跨系統傳輸須符合廠內規範。
  • 邊緣資源： 依設備的 CPU、記憶體與加速器決定模型大小、推論頻率與緩衝策略。
  • 偵測可用性： 除準確率外，也要評估誤報率、漏報率、告警量與現場負擔。
  • 設備安全與故障隔離： AI 只提供異常判斷與維護建議；涉及安全的控制仍由經驗證的控制系統與安全機制負責。

02. 端到端技術架構#

架構分為六層。前三層取得、串流並萃取特徵；第四層形成判斷；第五層把判斷轉成任務；第六層負責系統整合與安全控制。

層級名稱主要技術與職責
01感測與資料擷取MCU、IO-Link、振動／電流／壓力感測器
02串流與時序資料Kafka、InfluxDB、環形緩衝區、資料時間戳與同步
03訊號處理FFT、小波轉換、時域與頻域特徵萃取
04AI 分析與 PHMIsolation Forest、Autoencoder、LSTM／Transformer、RUL 預測
05Edge Agent 與任務協調狀態管理、工具路由、工作流程編排、模型選擇
06整合與安全控制SECS/GEM、MES／EAP API、權限驗證、安全中介層

邊緣端負責低延遲處理與推論，集中式平台負責模型管理、跨設備分析與部署。Kafka 負責訊息傳遞、降低資料流耦合；InfluxDB 保存與查詢時序資料；環形緩衝區則處理需要穩定記憶體用量的連續資料。這些元件不必串成單一路徑，組合取決於資料頻率、延遲需求與部署環境。即使模型可在數毫秒內回傳，端到端延遲仍須計入擷取、訊號處理、推論、通訊與控制器執行。

03. 高吞吐資料串流與訊號處理#

高頻感測的第一個問題通常不是準確率，而是持續湧入的資料。

資料量估算與計算範圍#

以 20 台設備、每台 3 個感測通道、每通道 2 kHz 連續取樣、每筆數值 4 bytes 估算。

每秒：

$$ 20 \times 3 \times 2{,}000 \times 4 = 480{,}000\ \text{bytes/s} $$

每日：

$$ 480{,}000 \times 86{,}400 = 41{,}472{,}000{,}000\ \text{bytes/day} $$

約 41.47 GB／日（十進位，1 GB = \(10^9\) bytes）。這只計入原始數值，未含時間戳、封包、索引、儲存格式與其他中繼資料；若將這些成本計入，規劃上可用 50 GB／日估算，實際取決於格式與保存策略。

20 台只是示例，不是規模宣稱。設備納管規模（可連線台數）與高頻處理規模（實際以 2 kHz 串流原始波形的台數）是不同指標，後者取決於啟用高頻取樣的設備數、通道數、取樣頻率與保存策略；納管 500+ 台不代表全部都以該頻率傳輸。

訊號處理流程#

資料管線可拆成四個階段：

  1. 擷取： 取得振動、電流、壓力訊號，處理時間戳、缺值與資料品質。
  2. 視窗化： 將連續訊號切成固定長度視窗，長度與重疊依設備與分析任務決定。
  3. 特徵萃取： 以 FFT、小波轉換與統計方法計算 RMS、頻譜熵與頻帶能量。
  4. 輸出： 產生固定格式的特徵向量，供異常偵測與健康度模型使用。

模型可改用 64 維特徵向量取代完整波形，降低下游運算，但是否適合仍取決於異常型態與模型需求；萃取時遺失的資訊無法還原。

邊緣端最佳化#

可從幾個方向著手：

  • 以批次或視窗處理，並用預先配置的環形緩衝區減少記憶體配置與複製。
  • 將高頻訊號處理與較低頻率的狀態分析分開執行。
  • 對原始資料、特徵與事件採不同的保存與傳輸策略。
  • 監控佇列長度、資料遺失、CPU 使用率與端到端延遲。

04. 雙層異常偵測#

設備故障資料嚴重不平衡：正常資料容易取得，真實故障稀少，監督式學習因此缺乏足夠的故障標籤。

誤報是另一實務問題。最常見來源是換料或暖機，振動頻譜短暫偏離正常，模型卻連續告警——久了現場就開始忽略系統。

因此，架構把低成本的初步篩選與較深入的判斷分開。

第一層：快速篩選#

Isolation Forest 辨識偏離既有分布的樣本。它足夠輕量，適合資源受限的邊緣環境；任務是篩出值得進一步分析的資料，避免把所有異常分數都當成故障結論。

第二層：深入判斷#

Autoencoder 以重建誤差比對學習到的正常模式。門檻可依設備類型、運作狀態與感測通道設定，避免把正常製程切換或負載變化視為故障。

告警整併與抑制#

告警管理不能只看模型輸出：須考慮重複告警、持續時間與嚴重度、設備運作與維修狀態，以及是否已確認或建立工單。同設備、同異常類型設五分鐘重複抑制是合理起點，但嚴重度升級與安全事件須保留例外，不能為了減少通知而遮蔽新風險。

05. 設備健康管理與剩餘壽命預測#

異常偵測回答「是否偏離正常」，預測性維護則回答「健康度如何變化、何時需要維護」。

設備健康管理（PHM）整合感測特徵、設備歷史、故障模式與維護紀錄；資料足夠時，RUL 模型可估計距離特定失效條件還有多久。

RUL 模型設計#

  • 統計與存活分析： 例如 Weibull 存活分布，在合適假設下描述失效時間。
  • 時序模型： LSTM 或 Transformer，追蹤健康指標隨時間的變化。
  • 領域特徵： 結合頻帶能量、頻譜熵、振動幅度與負載，強化失效模式辨識。

三種方法的適用條件不同。Weibull 本身不能保證單一設備的 RUL 準確；個別設備仍須結合觀測與驗證。

從預測結果到維護安排#

RUL 的價值不只是產生一個時間數字，而是讓維護團隊提前安排人力、備品與停機時段。

  • 一般監控： RUL > 30 天，依既定頻率追蹤設備狀態。
  • 提前準備： 7–30 天，確認備品與維護資源。
  • 優先評估： < 7 天，安排工程師檢查並評估維修時程。

這些區間只是示例，實際門檻取決於故障後果、備品交期、預測不確定性與產線排程。涉及安全風險時，不能只靠 RUL 決定是否繼續運作。RUL 是統計估計，不是保證；維護區間必須保留人工複核，不能直接變成停機指令。

06. 邊緣部署與模型生命週期管理#

訓練完成後，下一個問題是穩定部署到不同設備與產線，並在更新失敗時回到原版本。部署不只是打包容器：作業系統、硬體架構、驅動、推論引擎版本與設備通訊方式，都會影響模型能否執行。因此，流程可拆成四個階段。

1. 標準化封裝#

將模型、推論程式、依賴套件與設定檔打包成可追蹤的版本，並依硬體平台建立相容性測試。

2. 影子部署#

新模型與現行模型或規則並行，不影響正式控制；比較輸出、延遲、資源使用與代表性故障案例。影子期間應涵蓋具代表性的設備狀態；兩週是參考週期，不適用於故障稀少的設備。

3. 金絲雀分批發佈#

先在少量設備部署，再推進到 5%、20%，最後 100%，每個階段都要有明確驗收門檻。

4. 監控與回退#

追蹤推論失敗率、延遲、資源使用與輸出分布。超過門檻就停止擴大部署，並依事先定義的流程回退至已驗證版本。

07. Edge Agent：任務協調與決策邊界#

Edge Agent 把感測資料、模型推論、設備狀態與維護流程整合成可追蹤的工作流程。它不必每次決策都呼叫 LLM：延遲要求明確、輸入輸出固定的任務，用傳統邏輯或輕量模型更容易測試；Agent 適合跨工具協調與多步驟執行。

邊緣端的任務分工#

  • 即時訊號處理： 在邊緣完成擷取、特徵計算與必要的低延遲推論。
  • 狀態判斷與任務協調： 整合異常分數、RUL、設備狀態與維護紀錄，決定是否檢查或建立工單。
  • 設備控制與安全： 由具明確控制邏輯與安全驗證的系統執行；自由生成文字或未驗證的模型輸出，絕不能直接成為高風險控制指令。

LangGraph 等工作流程框架可管理狀態、工具呼叫、重試與分支；Model Router 依任務複雜度、延遲與運算資源選擇模型或規則引擎。但框架不保證即時性或安全性。

斷線時的處理策略#

網路斷了，Agent 該繼續做，還是該停？這是邊緣系統一定會遇到的情境。

必要的監控與本地狀態判斷仍依既定規則運作；若系統無法確認自身狀態，就進入預先定義的降級模式。各設備在降級時的行為，須由設備風險分析決定，不能交由通用 Agent 推斷。部分設備可能需要降載，有些則應停止特定動作或交由既有控制器接管。

這裡需要區分三個概念：

  1. 離線可用性： 網路中斷時，本地監控或推論能否繼續。
  2. 任務成功率： Agent 能否完成工具呼叫、狀態更新與工單建立。
  3. 設備安全性： 通訊中斷或任務失敗時，既有控制器是否仍保護設備。

三者評估方式不同，Agent 任務成功率不能代替設備安全驗證。OHT（Overhead Hoist Transport，空中搬運車）與其他高風險設備，仍須靠獨立安全機制與驗證程序。

08. 工業 RAG：讓設備知識可以被檢索與追溯#

工廠知識不只在設備手冊，也散落在維修日誌、異常報告、工程筆記與歷史工單。格式與品質不一，直接丟進向量資料庫，可能生成流暢但不正確、也不適用於當前設備狀態的答案。工業 RAG（Retrieval-Augmented Generation）的重點因此是可追溯：把問題、檢索證據與原始文件連起來。

知識處理流程#

  1. 文件整理與權限： 轉換格式、去除重複、辨識版本、處理敏感資料，並保留來源與權限。
  2. 語意切分與索引： 依文件結構與內容切塊，再產生向量表示。
  3. 混合檢索： 結合 BM25、向量檢索與 Metadata 過濾，應對專有名詞、設備編號與相似文件造成的檢索問題。
  4. 重排序： 重新評估候選文件與問題的關聯性。
  5. 答案生成與引用： 依檢索證據作答，並提供文件、版本與頁碼供核對。

企業環境中的限制#

在工廠部署 RAG 還須落實文件層級權限控管、防止未授權資料存取，並處理互相矛盾或過期的文件。

維修建議應區分文件記載與模型推論；證據不足時，系統應直說，而不是補出一套看似完整的程序。文件索引與查詢紀錄也需依敏感度設定保存期限、稽核方式與存取權限。檢索到的文件與工具輸出都應視為不可信輸入；提示注入或遭汙染的文件，不得擴大權限或觸發控制動作。

09. MLOps：模型上線後的持續監控#

模型在測試集表現良好，然後呢？

零件老化、維護作業、負載或製程變化，都會讓資料分布偏離訓練。模型上線後因此需要持續監控，以及從偵測、評估到更新的流程。

漂移監控#

可用 PSI（Population Stability Index）、KS 檢定或其他分布差異指標對照基準。PSI 超過 0.25 是常見警示門檻，但超標不代表模型失效；門檻應依資料分布、特徵行為與驗證結果設定。也要監控資料缺漏、感測器異常、推論延遲與輸出分布，避免把感測器故障誤判為漂移。七日滾動基準不應吸收發展中的異常；應依運作模式建立動態基準，加上異常檢查與明確的更新條件。

模型更新流程#

較完整的流程包含：

  • 定期評估資料品質與模型表現。
  • 針對確認的問題建立候選模型，並在歷史與模擬資料上驗證。
  • 以影子模式比較新舊版本，審核後分批發佈。
  • 保留版本、資料來源、參數與驗證紀錄，以利追蹤與回退。

自動化不是一偵測到漂移就立刻換模型，而是縮短偵測、評估與部署時間，同時讓過程可控、可稽核。

10. 系統整合與後續發展方向#

前面各節解決不同層次的問題：串流確保資料能穩定取得與分析，異常偵測與 RUL 提供狀態判斷，Agent 協調任務，RAG 補上可追溯的文件知識，MLOps 管理模型生命週期。

這些元件必須透過清楚的資料介面、權限與錯誤處理整合。把服務接起來，並不會自動形成自主決策系統。

1.0：建立可觀測、可預測、可維運的基礎#

第一階段讓每個元件都有明確輸入輸出、可量測的監控指標與故障處理，並在限定設備與產線驗證。

系統第一階段的重點評估指標
即時串流平台建立資料擷取與特徵處理流程吞吐量、資料遺失率、端到端延遲
異常偵測降低無效告警並保留重要事件誤報率、漏報率、F1-Score
RUL 預測提供設備健康度與壽命估計RMSE（均方根誤差）、預測區間與維護決策效益
Edge Agent協調模型、工具與維護工作流程任務成功率、延遲、失敗恢復能力
工業 RAG建立文件檢索與答案追溯機制檢索品質、答案正確性、引用可追溯性
MLOps建立模型版本與發佈流程部署週期、回退時間、版本追蹤完整度

2.0：從單點分析走向跨設備協作#

當單一設備的資料處理、模型品質與部署穩定後，才適合探索跨設備與跨產線協作。

  • 將處理擴展到更多設備，結合多感測器辨識複合異常，同時評估更高取樣率的頻寬與運算需求。
  • 讓 RUL 與備品管理、維護排程及工單系統整合。
  • 建立設備知識圖譜，支援跨文件、跨設備的關聯查詢。
  • 讓不同 Edge Agent 在授權範圍內交換狀態與任務結果。

長期可探索 Edge Agent Swarm，讓多個代理跨設備或任務協作；但這會帶來狀態一致性、任務衝突、通訊失敗、權限與錯誤擴散，必須先定義責任、可執行動作與失敗處理。

11. 結語#

智慧工廠邊緣 AI 不是把感測器、模型與 Agent 框架湊在一起就能完成。真正的工作是系統工程：可靠的資料、能在受限資源下執行的模型、值得信任的異常結果、部署失敗時的安全回復，以及不破壞既有安全機制的 AI 建議。

預測性維護與自主決策 Agent 不是兩件事：前者提供狀態與風險資訊，後者把它轉成可追蹤的工作流程。資料治理、模型監控與安全控制讓系統長期可靠。重點不是第一天就完全自主，而是先讓每個環節可觀測、可驗證、可回退，再擴大 AI 參與的決策範圍。這也是讓 AI 真正走進工廠現場的前提。

附錄：效能數字的最低檢查#

本文刻意不列專案績效數字，只保留可重算的估算與設計門檻。若引用同類數字，以下四點是最低限度的檢查。

一、來源與範圍。 確認原始測試紀錄是否可追溯、數字是否經獨立驗證；公司、客戶、設備與系統資訊是否已去識別化或概括化。

二、量測基準比數字重要。 同一指標在不同定義下可能差一個數量級：延遲與冷啟動看起訖點，誤報率看分母，可用率看統計期間與判定條件，文件量與映像大小看計算範圍。平均值也應搭配分布與尾端值。

三、不可單一歸因。 停機、維護成本、異常停機率與節省工時，同時受流程、備品策略、設備更新與人員分工影響；若無法拆出模型貢獻，不宜全歸功於 AI。

四、不是產業基準。 數字成立於特定設備、負載與部署條件；換一條產線或故障型態，結果可能完全不同。

本文不構成任何設備操作、安全控制或維護決策的依據。
