小模型不像是大腦：0.8B 小型語言模型 × Pokémon Red 的 Harness 工程

用 0.8B 本地 SLM 玩 Pokémon Red，從 VLM 截圖的 1–2 秒延遲與幻覺，改用 RAM／TileMap 的 0.01 ms 觀測，再用三層 Agent Harness 把反射、記憶與導航從模型身上拆出去。這是一場把小型語言模型放對位置的工程實驗，不是模型評測。

TL;DR

0.8B 的價值，是在一個被整理好的世界裡做選擇。

我一開始把遊戲畫面丟給同一個 0.8B 模型，讓它看圖決定按鍵。結果跑了 22.5 分鐘、132 個 episode（平均每個約 10 秒），動作欄位只有一個值：A，畫面還停在標題。後來我沒換更大的模型；我把「看畫面」改成「讀 RAM」，把「記路」從模型手上拿走，它第一次自己走出了家門，抵達 Pallet Town（真新鎮）。

這篇是 Agent Harness 的工程記錄，重點是感知、記憶、導航、反射這四件事：哪些該交給模型，哪些不該。

0. 按了 132 次 A，還在標題畫面#

專案的 SQLite 裡躺著一段很難看的紀錄。

132 個 episode，動作欄位只有一個值：A。最後一次狀態仍是 title，其中 10 筆被標記為 stuck_detected。如果把這段 log 貼給任何人看，得到的結論大概都是：「0.8B 太笨了。」

我一開始也這樣想。

但把時間軸拉長，會看到另一個問題。它被塞進一張 120×96 的截圖裡，同時要做 OCR、地圖辨識、座標定位、碰撞判斷、路徑規劃與按鍵控制。任何一個環節錯了，下一步就沒有意義。模型連「自己在哪裡」都不知道。

那不是模型笨，是我把太多工作塞給同一個模型。

1. 六篇 SLM 文獻，拼出同一個結論#

為了確認這不是自己的錯覺，我把手邊六篇 SLM 相關論文重新讀了一次。它們的證據類型不同，但放在一起，剛好可以解釋這個專案為什麼會失敗、又為什麼後來能動。

不過，Belcak 等人的 SLMs are the Future of Agentic AI 是 NVIDIA 的 position paper，不是中立綜述；Lee 與 Berg-Kirkpatrick 的 Readability ≠ Learnability 是訓練研究，不能當成 agentic system 的 benchmark。把它們當成「共識」會過度解讀。

但其中有一個觀察，和這個專案的體感很接近。Sharma 與 Mehta 的 SLMs for Agentic Systems 指出，對很多 agentic workload 而言，主要瓶頸經常是 orchestration 與 I/O，而不是模型的長程世界知識。它把 SLM 定位成多數 agent pipeline 的預設引擎，只在開放域推理與長程規劃等真正困難的環節，才呼叫更大的 LLM。

我的結論是：

如果問題是「開放式世界知識」，0.8B 一定輸。 如果問題是「在幾個結構化選項裡做選擇」，0.8B 可能夠用。

這篇文章要測的是：

把哪些工作從 0.8B 拿走之後，它就能玩？

我實際跑的是 qwen3.5:0.8b。這個任務的瓶頸不在知識量，所以我不需要更大的模型。與其把預算花在參數，不如先確認模型看見了什麼。

2. 為什麼是 Pokémon Red#

Pokémon Red 不是一個公平的 benchmark。它是一個很方便的 stress test。

它有四個特性：

  1. 部分可觀測：玩家只能看到當下畫面，但遊戲的真正狀態藏在 RAM 裡。
  2. 延遲敏感：Game Boy 的移動、對話、選單都有自己的 frame 節奏，按太快或太慢都會失效。
  3. 長時序：一步走錯不會馬上爆炸，但會在半小時後變成「卡在房子裡」。
  4. 可重現：模擬器、存檔、RAM map 都是公開的，錯誤可以反覆重跑。

Pokémon Red 的 RAM map 有社群整理（DataCrystal 的 RAM map 頁面），所以我可以把「觀測」從像素換成狀態，專心測試 harness。如果今天換成一款沒有 RAM map 的遊戲，VLM 或 OCR 可能仍是唯一的路。

本文不會散布 ROM。遊戲本體請使用自己合法取得的副本。

3. 第一版：把畫面丟給模型#

第一版是 VLM（視覺語言模型）pipeline，做法很直覺：

flowchart LR
    A[PyBoy 畫面<br/>160×144] --> B[縮圖 120×96<br/>NEAREST 放大回 160×144]
    B --> C[Base64 PNG]
    C --> D[qwen3.5:0.8b]
    D --> E[單一按鍵]
    E --> F[PyBoy 下一幀]

Game Boy 的原生解析度是 160×144。我以為把畫面縮到 120×96 再放大回 160×144，可以降低 base64 大小，於是就這樣送進模型。這個「最佳化」是第一個致命傷：120×96 不是 160×144 的等比例縮放，8×8 的字元被壓成約 6×5.3，對話框、選單、數字與地圖細節全部糊掉。更諷刺的是，繞了一圈又回到 160×144，base64 不一定變小。先失去的細節卻回不來了。如果重來，我會用 120×108，至少保住 10:9 的比例。

第二個致命傷是 prompt。我當時只問：

你正在玩 Pokémon Red。看這張截圖，選一個最好的下一個按鍵。只輸出 UP、DOWN、LEFT、RIGHT、A、B、START、SELECT、NONE。

沒有地圖名稱、沒有座標、沒有碰撞資訊、沒有行動歷史。模型看到的是一張縮圖，卻要回答一個需要狀態的問題。

後來加上狀態抽取器，情況也沒有好轉。JSON schema 裡只有 location_hint、summary、confidence 這些欄位，而且 prompt 還明寫「不要從像素猜精確座標」。於是模型給出的就是「看起來像在房間裡」這種描述。對人類來說這很合理，但 agent 要決定「往左還是往右」，這種描述等於沒有觀測。

延遲也是災難。視覺模式把推論間隔設為 1 秒，實際每次決策約 1–2 秒。如果主迴圈同步等待，遊戲就會定格。MacBook 的 M 系列晶片又是 CPU/GPU 共用記憶體，PyBoy 的模擬與顯示、Ollama 的推論共享同一塊記憶體與 GPU 資源，兩邊一起搶，風扇先受不了。

那段 132 次 A 的紀錄，就是這個階段的極端結果。模型沒有隨機亂按；它收斂到一個最保守的動作：既然不知道自己在哪，按 A 不會移動，至少不會立刻撞牆。

我沒有因此認為視覺模型沒用。視覺不是錯，錯的是用視覺去讀一個已經有結構化記憶體的世界。

4. 第二版：RAM 是更好的眼睛#

Pokémon Red 的 RAM 是公開的。地圖 ID、玩家座標、面朝方向、戰鬥狀態、隊伍 HP、徽章、金錢、背包，全部有固定位址。與其讓模型從像素猜，不如直接讀。

位址內容
0xD35E地圖 ID
0xD361 / 0xD362玩家 Y / X 座標
0xC109面朝方向
0xD057戰鬥狀態（0/1/2）
0xCFD8敵方精靈 ID
0xCFE6–0xCFE7 / 0xCFE8敵方 HP / 等級
0xD163隊伍數量
0xD16C–0xD16D / 0xD18D–0xD18E當前 HP / 最大 HP
0xD18C等級
0xD173–0xD176四招招式 ID
0xD188–0xD18B四招剩餘 PP（使用次數）
0xD16F異常狀態
0xD356徽章 bitfield（popcount 後才是數量）
0xD347–0xD349金錢（BCD）
0xD31D背包物品列表（數量在 0xD31C）
0xCD38腳本化按鍵模擬索引（非 0 時停用碰撞）
0xC3A0–0xC507wTileMap，20×18 的螢幕文字層

0xCD38 是 wSimulatedJoypadStatesIndex；它讓遊戲模擬按鍵，非 0 時會停用碰撞，但不是完整的控制鎖定。真正的按鍵忽略旗標是 wJoyIgnore。

讀取本身很短：

def u8(addr: int) -> int:
    return self.pyboy.memory[addr]

state = {
    "map_id": u8(0xD35E),
    "y": u8(0xD361),
    "x": u8(0xD362),
    "facing": u8(0xC109),
}

上面是簡化版。實際專案裡，這層還有 16-bit big-endian、BCD 金額與 event bit 三種讀法：

pokemon_reverse.py · RAM 讀取原語 python · 20 行 
    def read_byte(self, addr: int) -> int:
        return self.pyboy.memory[addr]

    def read_event_bit(self, addr: int, bit_idx: int) -> bool:
        """Reads an individual event bit formatted like 0xD74B-idx where idx 0 is MSB."""
        val = self.read_byte(addr)
        return f"{val:08b}"[bit_idx] == "1"

    def read_word_be(self, addr: int) -> int:
        """Big-endian 16-bit word."""
        return (self.pyboy.memory[addr] << 8) | self.pyboy.memory[addr + 1]

    def read_bcd_money(self) -> int:
        """Reads 3-byte BCD money at 0xD347-0xD349."""
        def bcd(b):
            return ((b >> 4) * 10) + (b & 0x0F)
        b2 = self.read_byte(0xD347)
        b1 = self.read_byte(0xD348)
        b0 = self.read_byte(0xD349)
        return bcd(b2) * 10000 + bcd(b1) * 100 + bcd(b0)

搭配 Game Boy 的 charmap 解碼，wTileMap 可以直接還原對話框、選單項目與游標位置。這些字元是遊戲自己寫進記憶體的事實，不需要 OCR 猜。

    def decode_text_bytes(self, byte_list: List[int]) -> str:
        """Converts raw Pokemon Red encoding bytes into a readable string."""
        chars = []
        for b in byte_list:
            if b == 0x50:  # string terminator
                break
            ch = POKEMON_CHAR_MAP.get(b, "")
            chars.append(ch)
        return "".join(chars)

    def extract_screen_tilemap(self) -> Tuple[List[str], List[str], Optional[str], str]:
        """Reads the 20x18 Game Boy TileMap from wTileMap (0xC3A0 - 0xC507).

        Returns:
            (all_text_lines, menu_items, selected_menu_item, dialogue_text)
        """
        all_lines: List[str] = []
        dialogue_lines: List[str] = []
        menu_items: List[str] = []
        selected_menu_item: Optional[str] = None

        for row in range(18):
            row_bytes = [self.read_byte(0xC3A0 + row * 20 + col) for col in range(20)]
            decoded_row = "".join(POKEMON_CHAR_MAP.get(b, " ") for b in row_bytes)
            cleaned = decoded_row.strip()

            if cleaned:
                all_lines.append(cleaned)

                # Check for menu cursor ▶
                if "▶" in cleaned:
                    parts = cleaned.split("▶", 1)
                    item_name = parts[1].strip().split()[0] if parts[1].strip() else "Option"
                    selected_menu_item = item_name
                    menu_items.append(f"▶{item_name}")
                elif row < 12 and any(keyword in cleaned for keyword in ["PKMN", "ITEM", "RUN", "SAVE", "OPTION", "EXIT", "YES", "NO"]):
                    for w in cleaned.split():
                        if w and len(w) > 1 and w not in menu_items:
                            menu_items.append(w)

        # Check if lower screen has a true Game Boy dialogue box frame (Row 12: 0x79 0x7A...)
        r12_b0 = self.read_byte(0xC3A0 + 12 * 20)
        r12_b1 = self.read_byte(0xC3A0 + 12 * 20 + 1)
        has_dialogue_frame = (r12_b0 == 0x79 and r12_b1 == 0x7A)

        if has_dialogue_frame:
            for row in range(13, 17):
                row_bytes = [self.read_byte(0xC3A0 + row * 20 + col) for col in range(1, 19)]
                line_str = "".join(POKEMON_CHAR_MAP.get(b, " ") for b in row_bytes).strip()
                line_str = line_str.replace("▶", "").replace("▼", "").strip()
                if line_str and sum(c.isalpha() for c in line_str) >= 2:
                    if not any(kw in line_str for kw in ["FIGHT", "PKMN", "ITEM", "RUN", "EXIT", "SAVE", "OPTION"]):
                        if line_str not in dialogue_lines:
                            dialogue_lines.append(line_str)

        dialogue_text = " ".join(dialogue_lines)
        return all_lines, menu_items, selected_menu_item, dialogue_text

依專案 README 的自測值，這一層的讀取延遲小於 0.01 ms。這是專案自測，量測方式也很土：在同樣的 Python 迴圈裡連續讀幾次，抓個大概。但它和「1–2 秒的截圖推論」差了好幾個量級。

前後對照大概是這樣：

代價也很清楚：這是 ROM-specific 的解法。換一款遊戲，RAM map 要重找；換一個平台，charmap 要重寫。這種解法成立的前提，是世界本身有結構。

5. 三層 Harness：把「聰明」拆開#

Layer 0：反射#

對話框出現就按 A，過場動畫就等待，選單有 YES/NO 就確認。這些規則明確、延遲要求高，交給模型反而變慢。

Layer 0 的優先順序最高。程式只要看到 screen_type == "dialogue"，就不會去問模型「你覺得要不要按 A」。這樣做是為了不浪費它的時間，跟信不信任無關。

Layer 1：空間記憶#

Layer 1 維護三種東西：

  • seen_coords：走過的格子。
  • blocked_moves：(map_id, x, y, direction) 的碰撞邊界。
  • discovered_warps：走過的門、樓梯、入口。

然後用 BFS（廣度優先搜尋）找最近的未探索 frontier，或走到已知出口。這層完全不需要語言模型。它要的是全域路徑、碰撞檢查與一致性。

memory_system.py · find_frontier_exploration_step python · 55 行 
    def find_frontier_exploration_step(
        self,
        map_id: int,
        start_pos: Tuple[int, int],
        max_depth: int = 80,
    ) -> Optional[str]:
        """Finds the closest unvisited coordinate (frontier tile) and returns the first step direction.

        CRITICAL FIX: Known warps and locked entry stairs are NEVER treated as frontier exploration targets!
        """
        sx, sy = start_pos
        known_warps = self.get_known_warps(map_id)
        queue = deque()
        visited = {start_pos}

        for dir_name, (dx, dy) in DIR_VECTORS.items():
            nx, ny = sx + dx, sy + dy
            if (map_id, sx, sy, dir_name) in self.blocked_moves:
                continue
            # If entry warp is on cooldown, cannot step directly onto it
            if self.is_warp_cooldown_active() and (nx, ny) in self.current_entry_warps:
                continue
            if (map_id, nx, ny) not in self.seen_coords:
                # Discovered warps are portals, NOT unexplored floor frontiers!
                if (nx, ny) not in known_warps:
                    return dir_name
            visited.add((nx, ny))
            queue.append(((nx, ny), dir_name))

        steps = 0
        while queue and steps < max_depth:
            steps += 1
            (cx, cy), first_dir = queue.popleft()

            for dir_name, (dx, dy) in DIR_VECTORS.items():
                nx, ny = cx + dx, cy + dy
                if (nx, ny) in visited:
                    continue
                if (map_id, cx, cy, dir_name) in self.blocked_moves:
                    continue
                if not (0 <= nx <= 80 and 0 <= ny <= 80):
                    continue
                # Do not path through active cooldown entry warps
                if self.is_warp_cooldown_active() and (nx, ny) in self.current_entry_warps:
                    continue

                if (map_id, nx, ny) not in self.seen_coords:
                    # Ignore warps as frontier targets
                    if (nx, ny) not in known_warps:
                        return first_dir

                visited.add((nx, ny))
                queue.append(((nx, ny), first_dir))

        return None

Layer 2：0.8B 的策略#

模型拿到的是整理過的狀態：地圖名稱、座標、可行方向、障礙方向、NPC 線索、frontier 方向、上一個動作。模型的輸出是一個動作（方向或互動鍵），必要時附帶 1–3 步的步數。

依 README 的自測值，文字模式推論約 10–50 ms。這個數字同樣是專案自測，不是獨立 benchmark；但至少說明，當輸入是結構化狀態時，0.8B 不需要很長的思考時間。（這次 log 的 latency 欄位量的是 Ollama HTTP 往返，包含排隊與網路層，不是這個數字；兩者邊界不同。）

模型收到的 prompt 長這樣：

def ollama_worker(
    task_queue: queue.Queue,
    result_box: dict,
    brain: OllamaBrain,
    min_interval: float,
    stop_event: threading.Event,
):
    """Background worker thread that queries Ollama without blocking PyBoy."""
    last_inference_time = 0.0

    while not stop_event.is_set():
        try:
            task = task_queue.get(timeout=0.2)
        except queue.Empty:
            continue

        if task is None:
            break

        state, image, last_action, is_stuck, memory_context = task

        now = time.time()
        elapsed = now - last_inference_time
        if elapsed < min_interval:
            time.sleep(min_interval - elapsed)

        try:
            action, steps, latency, raw_text = brain.decide_action(
                state=state,
                image=image,
                last_action=last_action,
                stuck_detected=is_stuck,
                memory_context=memory_context,
            )
            result_box["action"] = action
            result_box["steps"] = steps
            result_box["latency"] = latency
            result_box["raw_text"] = raw_text
            result_box["ready"] = True
            last_inference_time = time.time()
        except Exception as e:
            log.error(f"Inference worker error: {e}")
            result_box["action"] = "A" if state.screen_type == "dialogue" else "DOWN"
            result_box["steps"] = 1
            result_box["latency"] = 0.0
            result_box["raw_text"] = "FALLBACK"
            result_box["ready"] = True
        finally:
            task_queue.task_done()

按鍵也有時序校正，單位是 Game Boy 的 60 Hz 幀：方向鍵按住 12 幀、放開 12 幀，總共 24 幀；A/B 這類非方向鍵是按住 8 幀、放開 10 幀。按太快，遊戲只會轉向不會走；按太慢，一個 tile 的移動會拖成兩步。

這種分層在機器人學裡很常見：慢速 planner + 快速 controller。在這裡，planner 是一顆 0.8B 的語言模型，controller 是 BFS 與反射規則。

6. 四個卡點#

6.1 Warp 不是 frontier#

Agent 第一次卡住，是在房子裡上樓、下樓、再上樓。

原因是 BFS 對 frontier 的定義太單純：沒走過的格子就是未探索。但樓梯與門口也是「沒走過」的格子，卻不是房間的一部分。模型看到 frontier 在樓梯口，就走過去。一走過去就被傳送到另一層。另一層的 BFS 又把剛剛的入口當成 frontier，於是來回跳。

我把「門」從「房間」裡分離出來。

  • known_warps 不列入 frontier 目標。
  • 記錄 current_entry_warps，剛進來的那個入口要冷卻。
  • 一般冷卻 25 步；偵測到嚴重來回震盪時鎖 60 步。

BFS 現在追的是「還沒探索」的格子，已知的門直接排除。

BFS 排除 warp 只保證它不會把樓梯當目標，不能保證模型不會自己走過去。所以我在給模型的路況摘要裡把走過的 warp 入口標成 [B]，新出口才是 [D]。Prompt 直接寫明 [B] 是來時路，當前區域沒走完就不要踩。

6.2 四個方向都 blocked#

第二個卡點更荒謬。Log 長這樣：

Immediate Paths: Walkable -> [None] | Obstacles -> [UP, DOWN, LEFT, RIGHT]

四個方向都被標成牆。模型收到「沒有路」，探索建議也失效。Agent 站在一個理論上不可能存在的位置。

根因是碰撞網格把一次誤判累積成四面牆。可能是按鍵沒生效、可能是地圖切換瞬間讀到舊座標、也可能是一次移動被對話框打斷。只要有一次錯，那個 (map, x, y, direction) 就被永久標成 blocked。這層記憶沒有過期機制，錯誤會一直留著。

我加了兩層處理：

  • get_movement_options 偵測四個方向全 blocked 時，自動衰減，必要時清除這個位置的區域障礙。
  • Smart Unstick 在真的卡住時，從可行方向隨機挑一個，重新取狀態。

6.3 壞掉的碰撞網格被存下來#

第三個卡點更難查。Agent 不動了，但 stuck detector 沒有觸發。重開程式，還是在原地按 B。

因為壞掉的碰撞網格被持久化到磁碟了。程式重跑，讀回同一份「四面都是牆」的記憶，於是永遠找不到路。更糟的是，卡死檢測只看座標有沒有變。如果當下 screen_type 是選單或對話，它會刻意忽略停滯，避免把「按 A 翻頁」誤判成卡住。兩個機制疊在一起，就變成一個不會自己結束的迴圈。

後來的做法是：

  • 寫入磁碟前先驗證網格是否自相矛盾。
  • 地圖切換時重置局部障礙。
  • 不把「四個方向全 blocked」的狀態持久化。
  • 為這個案例加一個回歸測試。

原則：持久化錯誤比錯誤本身更貴。 一個會消失的 bug 還可以重跑；一個被寫進 state 的 bug 會跟著你到下一次啟動。

6.4 模型原地打轉#

最後一個卡點不是空間，是行為。模型連續輸出：

Action: DOWN 2
Action: DOWN 2
Action: DOWN 2

它看不見自己剛剛做了什麼。Prompt 裡有當前狀態，卻沒有行動歷史。0.8B 的有效上下文與指令跟隨能力有限，很容易把「往下走」當成預設答案。

最後我把決策空間縮小。

  • 把最近 N 個動作放進 prompt。
  • 加入停滯檢測，重複動作時強制換方向。
  • 只給四個方向與互動鍵，不給開放式指令。
  • 讓 Layer 1 在模型選到 blocked 方向時直接覆蓋。

兩邊比的不是同一件事。舊管線在標題畫面按了 132 次 A。新管線在 72 個格子、34 條碰撞邊界與 3 張地圖之間，完成了一次有意義的移動。

延遲不是一個數字，而是幾段不同量級的時間。先把新管線的 595 筆 episode 依 latency 欄位拆開：48 筆是 0（L1 BFS／節奏步，沒有呼叫模型），其餘 547 筆是 Ollama HTTP 往返。中位數 0.61 秒、p90 0.81 秒、p95 2.14 秒、最大 6.76 秒；504 筆在 1 秒內，41 筆超過 2 秒。這是端到端 HTTP 往返，不是模型本身的 inference time；README 的 10–50 ms 是另一個量測邊界，兩者不該直接相加或比較。

按鍵時序是固定的物理下限：方向鍵按住 12 幀、放開 12 幀，總共 24 幀（400 ms）；A/B 是 8+10 幀（300 ms）。模型回得多快，都還是要等這段時間。

上面這張圖不是「三種決策路徑」的量級比較，而是這次實際跑出來的分佈。舊的 VLM 1–2 秒是設計觀察，RAM 讀取 <0.01 ms 是專案自測；把它們放在同一條 log 軸上，會把不同量測邊界混在一起。

圖上那條灰色虛線是 timestamp 中斷 28 分鐘的位置；x 軸刻意用 episode 索引，不用 wall-clock，否則那段閒置會把整條曲線壓扁。曲線終點 71 格、記憶檔 72 格；差的 (5,5) 只出現在記憶檔。這種不一致我沒有硬湊。

不要把 0.01 ms 當成「RAM 萬能」。觀測變快了，決策還是原本的難題。加速來自整個 pipeline 的重新分工，單看一個數字會誤判。

8. 討論：SLM 的正確位置#

把這次實驗拆開，我會把 agent 的工作分成這樣：

工作交給誰為什麼
讀座標、地圖、對話RAM / TileMap確定性、低延遲、沒有幻覺
走路、避牆、找 frontierBFS + 碰撞記憶需要全域路徑，不需要語言
對話、選單、過場Layer 0 反射規則明確，模型反而增加延遲
高層策略、選目標0.8B SLM選項少、上下文短、需要一點常識
多跳推理、模糊語意更大的 LLM fallbackSLM 容易自信地猜錯

這張表大致對應前面的文獻回顧：SLM 適合當預設引擎，LLM 留給較難的個案。Belcak 等人的 position paper 更激進，但那是立場，不是定論。

Lee 與 Berg-Kirkpatrick 的研究則提醒我：該動的是介面，不是語言。我一開始也犯過類似的錯，以為 prompt 寫得更短、更口語，0.8B 就會更聰明。後來發現，把世界整理成四個方向、一個互動鍵、一份碰撞記憶，比寫一段更友善的 prompt 有用得多。

Whidden 的 Pokémon Red RL 實驗很容易被拿來對照。他用 PPO 開大量平行模擬器，reward 包含探索新格子、重複停留的懲罰、事件旗標與徽章。這類來回彈跳在訓練裡會被重複停留的負 reward 壓下去，最後變成 policy 的一部分。

這套方法不能直接搬到 0.8B。LLM 是 inference，決策時不會更新權重；不可能像 RL 那樣跑大量 episode 再回頭改模型。但 reward 的形狀可以借：新格子加分、重複停留扣分、剛走過的 warp 扣分。我沒有把 RL 放進這個專案，也不是說兩者等價。RL 用訓練時間換 policy；這裡用 harness 把問題縮小。

所以，什麼時候該用 SLM？

  • 動作空間是結構化的（按鍵、API、工具呼叫）。
  • 上下文不長，狀態可以壓縮。
  • 任務重複、專門，且錯誤可以檢查。
  • 你需要在本地跑，在意延遲、隱私或成本。

什麼時候該 fallback 給大模型？

  • 需要多跳推理或長上下文整合。
  • 語言本身有歧義，選項無法事先列舉。
  • 錯誤代價高，需要更強的世界知識與判斷。
  • 你要處理的是「沒見過的問題」，不是「見過很多次的問題」。

9. 結論：小模型不像是大腦#

我以前會把 agent 想成「一個很聰明的大腦，加上一些手腳」。這次做完，比較準確的畫面是反過來：

小模型不像是大腦。它比較像整個系統裡最會說話的那一層。

它負責在幾個被整理好的選項裡，選一個當下最合理的。讓 agent 變聰明的，是那個把世界整理成選項的 harness：可靠的觀測、會遺忘的記憶、能走路的導航、以及知道什麼時候不要問模型的反射層。

如果你也在做 edge agent，可以先問自己一個問題：

模型現在被迫做哪些不該它做的事？

把那些事拿走，0.8B 可能比你想像的更能幹。

下一步，我會把戰鬥策略、跨地圖的長期記憶與工具路由補上，也會試著讓 0.8B 與 4B／雲端模型分工：小模型處理常規決策，大模型在被需要時接手。

0.8B 不是終點。它是一個很好的預算單位。
